# LoopX as a Loop-Engineering Peer: Position on the Two-Axis Frame

## Abstract

LoopX [repo:README.md] is a local, agent-agnostic **control plane / state kernel for long-running AI agent work** ("loop engineering"). It externalizes durable control state — objective, gates, todos, claims/leases, evidence, quota, handoff — into an append-only event ledger and lets Codex / Claude Code / Cursor execute bounded turns while the kernel decides the next tick. Its stance is "*Keep the loop moving. Keep the judgment human.*" [repo:README.md, docs/product/vision.md].

Mapped onto the specification-gaming paper's two-axis frame [paper:§3.3], LoopX is a strong **Axis-A (flow-control completeness)** system with a **major Axis-B (verification-source decoupling) gap in production**, with one significant exception: its **benchmark/eval layer** is a concrete deployed instance of the two-axis evaluation the paper prescribes [paper:§5] and lists as its principal open problem [paper:§8.3]. In the read corpus LoopX does not name specification gaming; it reinforces the paper's §7 claim that industrial peers approximate the discipline without theorizing it [paper:§7].

This document reconciles two independent analyses (main-agent + third-party) into a single citation-grounded position, flagging every empirical claim for primary-source verification.

## 1. LoopX Essence

LoopX is **not a single-loop harness**; it is a **cross-turn, cross-agent, cross-runtime control plane** [repo:README.md, docs/architecture.md]. This places it in the negative space SolidForge "intentionally cedes" — "time-based re-fire and cross-cutting worktree-parallel sweeps to companion layers (declared non-interchangeable with the convergence loop)" [paper:§6]. LoopX substantiates the **time-based re-fire** half directly: its heartbeat scheduler drives recurring turns from a scheduler hint, and "recurring heartbeat or monitor work" is a named use case [repo:README.md] (identifier provenance psv-target, C12). It substantiates the **cross-turn / cross-agent continuation** dimension via durable claims/leases and typed handoffs (§2.1). The **worktree-parallel-sweeps** half remains SolidForge `parallel-development`'s domain; LoopX is adjacent, not substitutive, there. The comparison's central claim is therefore that LoopX and SolidForge are **complementary layers, not competitors**: SolidForge answers "how do I converge ONE artifact/feature with anti-spec-gaming discipline?"; LoopX answers "how do I keep a long-running objective's state stable, reviewable, and handoff-able across many bounded turns and peer agents?"

The state kernel is an **append-only event ledger with deterministic replay**: "canonical todo/history state moves to append-only events with deterministic replay, idempotent append, privacy partitions, and Markdown-compatible projections"; event classes are work / decision / accounting / evidence; "current state is a projection over those events" [repo:docs/architecture.md, docs/state-interaction-model.md].

## 2. Two-Axis Mapping

### 2.1 Axis A — near-textbook coverage of the three intrinsic modes

LoopX defends all three modes the paper names [paper:§2], though without using those labels. (The defense mechanisms are psv-admissible factual claims; the "anti-X mode" framing is an interpretive label — see psv_scope_note.)

- **Anti-context-rot**: compact inspectable evidence + authority sources replacing implicit model memory; "letting summaries replace writeback" is an explicit pitfall [repo:docs/product/foundations/loop-engineering-principles-and-pitfalls.md].
- **Anti-goal-drift**: lifetime-goal invariant + priority stack (P0/P1/P2) + a steering audit that forces picking from ≥3 candidates and re-ranking against P0/P1/P2 [repo:docs/product/foundations/loop-engineering-principles-and-pitfalls.md, docs/state-interaction-model.md].
- **Anti-error-compounding**: bounded one-segment-per-turn transitions + validation-before-writeback + checkpointed decisions with freshness checks [repo:docs/state-interaction-model.md].

### 2.2 Axis B — major production gap; concentrated in benchmark/eval

LoopX's **production** verifiers — defined here as the main agent loop's operational verifiers, **excluding the benchmark/eval subsystem** — are **all same-runtime**: the LoopX responsibility split is Agent → **Capability** (the per-call outcome normalizer/validator) → Provider → **Kernel** (durable-state committer), and "an observation is not a transition, and a provider receipt is not accepted progress until the capability validates it and the Kernel commits" [repo:docs/state-interaction-model.md]. The four production gates — `promotion_gate.py` (release-readiness evidence freshness; `non_blocking: True`), `operator_gate.py` (human decision-checkpoint; the source explicitly states this is NOT write-permission authorization), `authority.py` (source provenance), `boundary_authority.py` (write-scope permission) — are **authorization and hygiene gates, not correctness oracles** [repo:loopx/promotion_gate.py, loopx/operator_gate.py, loopx/authority.py, loopx/boundary_authority.py]. They do not defend against an agent satisfying its own proxy tests while missing intent [paper:§3.1]. The only structurally decoupled oracle in production is the **human operator**, framed as an *authority boundary*, not as spec-gaming defense [repo:docs/product/foundations/project-level-reward-model.md, docs/quota-allocation.md].

**Claim of absence (sampling-limited):** in the read corpus, no LoopX document uses "specification gaming," "proxy gaming," or "green tests wrong code," nor treats verification-source decoupling [paper:§4.1] as a design dimension. This is "not found in the read corpus," not proven global absence (C10).

The benchmark/eval subsystem is explicitly out of the "production" scope above, and is where the one strong Axis-B surface lives [repo:docs/development/benchmark-developer-workflow.md]: the official **Harbor** verifier — a benchmark scoring *environment/verifier* ("the official environment result is the scoring path... the official Harbor verifier remains authoritative"; invoked via `environment.exec()`) — scores outcomes (psv correction, C4-TIER: Harbor is an **externally-authored oracle**, paper §4.1 tier-3 strong decoupling, NOT a cross-family tier-2 model); an explicit Process/Outcome split is enforced (paraphrase of "Do not make `turn/completed` the benchmark success gate... require a committed, independently validated Turn before claiming treatment qualification"); and anti-gaming rules operate (anti-surrogate `packet_only_observation`; anti-prompt-only `historical_nonproduct_invalid_for_comparison`; anti-reward-leak "do not feed per-round reward to agents"; anti-timeout-gaming "do not repair verifier timeout by globally extending timeouts"; anti-fake-treatment "'the agent touched LoopX' is not enough"; matched arms — same case/source/model/reasoning/timeout/no-feedback). This is a concrete deployed instance of the two-axis *evaluation separation* the paper prescribes [paper:§5] (the process/turn-readiness metric kept distinct from an externally-authored outcome metric) — i.e., the two-axis *frame*, **not** the specification-gaming *injection set* the paper names as its still-open problem [paper:§8.3] (LoopX has separated metrics + anti-gaming controls, not a proxy-satisfying-but-intent-violating attack set). LoopX does not theorize the distinction. **Tier (psv-resolved, C4-TIER):** Harbor is an **environment/verifier** (§4.1 tier-3 strong decoupling — an externally-authored oracle whose blind spots are the benchmark test suite's, not the agent's), NOT a cross-family model (tier-2). The earlier "cross-family scorer" label was the author's gloss and is retracted; the Axis-B claim survives because tier-3 is strong decoupling.

A cross-runtime implementation-review demo (Claude implements, Codex reviews) [repo:docs/product/use-cases/cross-runtime/cross-runtime-impl-review-demo.md] is a tier-2 partial-decoupling instance [paper:§4.1] but is deliberately framed as workflow coordination, not spec-gaming defense — the doc states the intent to keep the demo "from becoming an argument between two models." The structural anti-self-approval rule (`must_not approve its own review gate`) is present; a blind-spot-divergence claim is not.

## 3. Process/Outcome Split — Enforcement Locus

The paper requires the Process/Outcome split to be **structural** (a schema invariant the agent cannot write), not **conventional** (a prompt the agent can route around) [paper:§4.2]. SolidForge implements this in its **specifier half**: blueprint-crafting emits a two-field verdict with `rightness: human_confirm_required` as a constant, field-isolated from the process axis ("a green process axis never changes the outcome-axis constant") [paper:§6, sf:blueprint-crafting]. (psv-scope correction, C15b: parallel-development, the implementer half, does NOT carry a rightness field — its run-record uses an `l4_assessment` maturity block + a dual-ring pass-clean DoD. The Process/Outcome invariant is a blueprint-crafting property; the "agent cannot write / schema-validation layer" enforcement is stated in paper §4.2 and embodied in `run_record.py`, not in the SKILL.md text itself.)

LoopX enforces **structurally at the spend and commit seams** (psv correction, C6c — the earlier "conventional at the act gate" framing was refuted by the source). Spend requires a fresh `quota should-run=should_run=true` — a **compute guard** ("may this goal spend another automatic turn now?"), NOT advisory (the source reserves "advisory" for `quota plan` and `goal_route_hint`) [repo:docs/quota-allocation.md]; durable state advances only on validated writeback ("Only validated writeback can change durable state or spend quota") [repo:docs/state-interaction-model.md]. There is no hard technical block on the executor performing read-only or non-advancing work, but **no state advancement or quota spend occurs without passing both gates**. The residual agent-loop-agnostic gap is narrower than "conventional at act": it is that **external/irreversible actions not mediated by the kernel** (an unmediated PR or external write) are not hard-blocked — the one place LoopX's positioning leaves a conventional, not structural, seam. So on the in-kernel path LoopX is *more* structural than a §4.2 "conventional" worry implies; the real §4.2 exposure is the out-of-kernel external-action surface. (The four-role split Agent→Capability→Provider→Kernel is verified verbatim in the README Runtime Responsibilities table.)

## 4. The Candidate-Salient Defense: `delivery_outcome` Enum

LoopX's `delivery_outcome` is a structured enum (`surface_only` / `outcome_gap` / `outcome_progress` / `primary_goal_outcome`) that drives quota spend [repo:docs/quota-allocation.md, docs/product/foundations/project-level-reward-model.md], paired with the pitfall "Counting every artifact as outcome progress" and the quota principle "Quota should count whether a turn produced a verified transition, not just whether an agent spoke" [repo:docs/product/foundations/loop-engineering-principles-and-pitfalls.md].

**Position (psv-resolved — downgraded):** psv adjudicated the two §4.3 preconditions against fetched sources and the defense scores **partially salient, partially latent** — weaker than the earlier "candidate salient." (C13) LoopX has a goal-owned objective and the executor is "not the source of truth" [repo:docs/state-interaction-model.md], but there is **no frozen executor-immutable intent blueprint** and no formal per-goal acceptance criteria, and eligible-peer executors can write active goal state — the §4.3 intent-blueprint precondition is only partially met. (C14) `delivery_outcome` is **executor-self-reported** via `refresh-state` [repo:docs/quota-allocation.md], and the kernel applies only **form-based frontier-delta validation** (IP-013/IP-024 normalize a no-change claim down to `outcome_gap`) — it does **not** check whether claimed progress matches the objective; there is no substance-based external-intent gate. Consequence: the defense **catches no-op / artifact-inflation claims** (the original artifact-count-Goodhart point — partially salient; the frontier-delta audit trail is auditable) **but an executor can satisfy the form check with an irrelevant frontier change and still claim `outcome_progress`** (partially latent). That latent residue is precisely the regime [paper:§4.3] assigns to heterogeneous oracles, which LoopX does not have in production. Honest classification: **partially salient, partially latent** — a real but partial Axis-A-adjacent defense, not the strongest among peers, and explicitly not an Axis-B engagement.

A directly absorbable corollary (contingent on the same two psv targets): SolidForge's `process_converged` is a boolean [paper:§6, sf:blueprint-crafting]; LoopX demonstrates a finer, still-process-side enum is feasible and useful — and would make salient artifact-gaming schema-visible rather than reliant on a reviewer reading the diff. This stays on the process axis and does not touch `rightness`.

## 5. Reward-Memory Self-Reward Firewalls

LoopX's Reward Memory is provider-neutral and Axis-A (preferences/steering/procedural), but is explicitly paranoid about becoming a same-source self-reward loop — the self-certification failure of [paper:§3.1] applied to a memory layer. Firewalls include: "inference never creates credentials, external-write capability, production permission"; "confidence describes evidence quality; it never increases authority"; "Issue Fix still verifies any recalled technical claim against current code and tests before it can affect a patch"; "it does not ingest raw chat or tool transcripts" [repo:docs/reference/protocols/reward-memory-architecture-v0.md].

A residual seam exists where the memory-ingest pipeline accepts a model-proposed compressed policy candidate (the reward-memory "compact candidate": a model-generated summary/abstraction of experience proposed for retention) as candidate memory. The stated defense is an authority checkpoint: the doc requires that "actor identity and repository/action authority must come from an independently verified source" and that "memory confidence cannot create or widen that scope." A 2nd-pass psv (C8b, expanded authority-chain sources) resolves this partially: the firewall is **decoupled from the model in its primary code path** — repository identity is read from git's own remote config (`loopx/repository_identity.py`), and approve/reject decisions come from the human operator gate (`loopx/operator_gate.py`); the doc forbids the model from creating authority ("Memory confidence cannot create or widen that scope"). It is therefore more than a same-source guardrail — a real structural decoupling in the primary path (the Axis-B framing is not falsified). It stays **narrowed, not verified**: the doc's "independently verified source" is never named (passive voice), GitHub-contributor identity is not established (only git-remote project identity), the operator gate is explicitly "not write-permission authorization," and several fallback/parameter-supplied code paths do not enforce external provenance at the function boundary — so decoupled-in-primary-path, not provably external-only across all paths.

## 6. Reward-Model Dimensions

LoopX's project-level reward model is `f(quantity, quality, token_cost, user_attention_cost)` [repo:docs/product/foundations/project-level-reward-model.md]. One dimension the paper's two-axis frame does not quantify: **user_attention_cost** — one of four co-equal reward inputs (psv correction, C9b: the phrase "Quota protects attention as much as compute" was a fabricated quote and is retracted; the dimension itself is verified). Under the **Quality** input sits a sub-indicator **"rework rate"** ("whether the user had to correct the same failure pattern again") [repo:docs/product/foundations/project-level-reward-model.md L51] (psv correction, C9c: it is a Quality sub-indicator, not a separate metric outside f(...)). It offers a more calibrated *internal* recurrence signal than boolean self-assessment — but it remains self-reported and does not address the external-ground-truth calibration gap the paper's §6 honest limitation (iii) names; it is not claimed here to partially close that gap.

4. **event-sourced append-only state kernel + deterministic replay** (the cross-turn state layer; paired with the heartbeat scheduler for time-based re-fire) → companion-layer pattern.
5. **frontier-delta-or-no-op invariant** — LoopX interaction-pattern catalog entry IP-024 ("the machine-visible work frontier is identical before and after a turn" → recorded as a no-op, not progress) [repo:docs/concepts/interaction-pattern-catalog.md] → SolidForge inner-ring anti-theater check.
6. **human-gate decision object** (question / blocked_route / safe_default / independent_work; the `decision_scope_v0` typed-scope enum — `kind` ∈ {private_read, write_scope, resource, production, public_claim, direction} × `granularity` ∈ {action, lane, goal, project, global}, exposed as a named todo rather than a vague "waiting on owner") [repo:docs/state-interaction-model.md] → operationalize `rightness=human_confirm_required`.
7. **user_attention_cost + rework_rate** metrics → SolidForge self-assessment block (with the §6 caveat that neither addresses external calibration).
8. **spend-after-validated-writeback + autonomous_replan_obligation** (quota discipline + anti-stall: consecutive stalled turns force a bounded replan, not another quiet no-op) → SolidForge convergence loop.
9. **peer leases/handoffs** (`(goal_id, todo_id)` soft claim → hard lease with TTL/idempotency/conflict-policy, no durable leader) [repo:docs/state-interaction-model.md] → SolidForge cross-session extension.
10. **Reward-Memory self-reward firewalls** (inference≠authority / confidence≠authority / current-artifact verification) → anti-latent-gaming for any steering/reward layer.
11. **public/private boundary scan gate** + compact evidence → SolidForge evidence discipline.
12. **typed vocabulary vs prose-shorthand layering** — LoopX distinguishes machine-checkable typed transitions (`LoopXTurnResultKind` etc.) from operator shorthand ("deliver/wait/ask"), so prompt-layer vocabulary drift cannot pollute the schema [repo:docs/state-interaction-model.md] → SolidForge skill convergence vocabulary.
