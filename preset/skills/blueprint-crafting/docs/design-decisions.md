# Design Decisions (ADR) — blueprint-crafting

On-demand reference. The non-obvious decisions behind this skill, with rationale and the alternatives rejected. Read before changing a foundational choice — reverting one of these without re-deriving the rationale reintroduces the problem it solved.

Format per entry: Context / Decision / Why / Rejected alternatives.

## 1. The plan-model is round-trip-compatible on the executable subset, not isomorphic

- Context: `arch-design.md` §6 originally claimed the plan-model is "isomorphic" to `parallel-development`'s `plan_queue.py` frozen queue. Verifying against `plan_queue.py`: its frozen queue is an implementation-grain format (`item_id / seq / depends_on / dod_ref / blueprint_subset`). The upstream plan-model needs to carry `complexity / risk / authority-chain / ODP-status / constraints-profile` (which the queue does not), and the queue carries `blueprint_subset` (a code-execution concern) which has no natural upstream source. So the two are neither identical nor isomorphic.
- Decision: the plan-model is **round-trip-compatible with the frozen queue on the executable subset** (`item_id / seq / depends_on / dod_ref`). Upstream-only metadata is carried as **tagged extensions**. Their consumption is **dual-mode** (amended when the rich path was added — see workspace `docs/rich-path-design.md`, `docs/odp2-verdict-design.md`, `docs/bc-pd-coupling-charter.md`): `parallel-development` **ignores them on the free path** (it re-normalizes arbitrary input, preserving R1/R2 independence) and **utilizes them on the rich path** when it detects a blueprint-crafting artifact (carries them faithfully per charter R4–R6). The three-way classification (executable / upstream_only / downstream_only) is unchanged; only the consumption framing moved from "ignore-only" to dual-mode. Downstream-only `blueprint_subset` has no upstream source and is left empty / marked "downstream-filled" at round-trip. ODP-3 is closed by this decision (implementation deferred, not open).
- Why: this is the minimal contract that lets the two skills compose without either (a) forcing upstream to carry code-execution concerns it cannot source, or (b) forcing `parallel-development` to understand upstream-only metadata.
- Rejected: "globally isomorphic" (false — the field sets genuinely differ, verified); "invent a brand-new shared format" (over-engineering); "upstream carries `blueprint_subset`" (no upstream source).

## 2. Determinism is over the normalized model, not over source

- Context: `arch-design.md` framed the inner ring as "deterministic" by analogy to `parallel-development`. But `parallel-development`'s inner ring operates on source that is already machine-form (code). This skill's inner ring is only deterministic **after** the normalizer has done graded extraction, and that extraction is semi-deterministic (latch = high confidence; prose = semantic-infer = low confidence). The framing hid this seam, risking a maintainer over-trusting `process_converged` as source-level determinism.
- Decision: state explicitly that **determinism holds over the normalized plan-model, not over the source documents.** The normalizer's graded extraction carries a confidence field; the constraints-checker's determinism is "on the model."
- Why: the seam is a legitimate design choice (borrow determinism from the target representation, not the source), but hiding it would let `process_converged` be read as stronger than it is. Surfacing it keeps the process/outcome axis separation honest at the operator level.
- Rejected: "fully deterministic over source" (impossible — prose dependency inference is heuristic); "abandon the dual-ring analogy" (it holds architecturally); "mark the whole checker non-deterministic" (wrong — it IS deterministic over the model).

## 3. Constrained production from the start; there is no "check-only" milestone

- Context: an earlier framing (v0.1–v0.3) split the skill into "v1 = consume + check" and "v2 = generation (deferred)," arguing generation was outcome-axis and should be deferred until the deterministic check-only v1 was solid. Reality correction: most upstream artifacts arrive incomplete, so the skill must author / rewrite / research / check them to convergence — generation is a core need, not a speculative v2. The check-only milestone would ship a skill that cannot do its job on real (incomplete) inputs.
- Decision: the skill performs **constrained production** (author / rewrite / research / check) from the start. Every activity has a **constraints-profile** — the deterministic checks that form its convergence oracle (process axis). Content correctness stays outcome axis (human). "Deterministic-first" now means **build the constraints layer first** (the oracle), not "ship check-only." There is no check-only milestone; production and checking are intertwined.
- Why: deferring generation under the "outcome-axis" label was a category error — generation IS convergeable *through its constraints* (sources-cited, anchors, authority, etc.), exactly as research is (ADR #4). The constraints are the process axis; only content correctness is outcome axis. Sequencing the constraints layer first preserves the deterministic-first principle without leaving the skill unable to handle incomplete inputs.
- Rejected: "v1 = check-only, v2 = generate" (the original — ships a skill that fails on real incomplete inputs); "generation is outcome-axis, defer indefinitely" (category error — generation has a deterministic process axis via its constraints); "ship generation without constraints first" (no convergence oracle — undercuts the whole thesis).

## 4. Research convergence oracle = its constraints-profile (sources / staging / trust / purity)

- Context: research is the activity most easily mis-classified as "pure outcome axis" (un-convergeable), because its content (is the conclusion true?) is genuinely human-only. But `ws-wiki/fedaot-kb` demonstrates a battle-tested model where research is **constrained production**: every synthesized claim must trace to a fetched source (sources-cited), output goes to a staging queue (never direct-published, defending against hallucination / timeliness / bias), is trust/provenance-tiered before promotion, has a direction-normalized idempotency key, is cost-bounded, and passes a purity filter. Each of those is a deterministic gate.
- Decision: research's convergence oracle is its **constraints-profile** — sources-cited, staging-status, trust/provenance-tier, direction-normalized (idempotency), cost-bounded, purity-filter (arch-design §3 research artifact). These are deterministic (process axis); the research *conclusion's correctness* stays outcome axis (human). The staging→promote step stays **human-gated** — the skill converges the constraints-profile, not the promotion decision.
- Why: this lets research be convergence-checked honestly without pretending the skill can judge the conclusion's truth. The constraints catch the failure modes that are detectable pre-use (unsourced claims, bypassed review, unbounded cost, non-reusable output); the human catches the rest at promotion. This generalizes the process/outcome split to the activity most people would assume is unconvergeable.
- Rejected: "research is outcome-axis, skip it" (wrong — it has a deterministic process axis); "direct-publish research once sources-cited" (rejects staging — loses the hallucination/timeliness/bias defense that fedaot-kb's pipeline documents); "auto-promote from staging when constraints pass" (promotion is a human outcome-axis decision); "adopt fedaot-kb verbatim" (ODP-4 resolve-now: adopt the pattern, decide the exact subset in I4).

## 5. The skill is named `blueprint-crafting`

- Context: naming was contentious across several rounds. Candidates: `upstream-crafting` (original), `intent-authoring`, `upstream-convergence`, `spec-and-design`, `blueprint-crafting`. Two corrections shaped the decision: (a) the skill does generation (author/research) as core, not deferred — so a generation-flavored name is honest, not overpromising; (b) the name is a **human-facing label** (a human browsing skills reads it), distinct from the doc-prose rule "AI agent as first reader" (workspace `CLAUDE.md` rule 10), so the name should be human-friendly and self-evident, not jargon.
- Decision: **`blueprint-crafting`**. "Blueprint" is the universal metaphor for "the detailed design/plan before construction" — exactly the upstream artifacts this skill produces (spec / arch-design / iteration-plan / research). It is human-friendly (a newcomer instantly grasps the scope), broad (covers all artifact types incl. research), and pairs with `parallel-development` (blueprint → development).
- Why: under the human-friendly criterion, "upstream" is relative jargon (upstream of what?) — not self-evident to a newcomer. "Blueprint" carries the meaning without the pipeline context. The collision with `parallel-development`'s "Intent Blueprint" concept is acceptable and arguably a feature: this skill crafts the materials that become the blueprint Phase 0 freezes.
- Rejected: `upstream-crafting` (relative jargon, weakest human-friendliness once generation is in scope); `upstream-convergence` (v1-honest but undersells once generation is core, and "upstream" jargon); `intent-authoring` (narrow — "intent" / "authoring" don't cover research); `spec-and-design` (concrete but list-y, misses plan/research).

## 6. Single skill with modes, not a skill family

- Context: blueprint-crafting handles multiple artifact types (spec / arch-design / iteration-plan / executable-plan / research) and activities (author / rewrite / research / check). ODP-2 asked: one skill with modes, or a family (e.g. spec-crafting / design-crafting / plan-crafting / research-crafting)?
- Decision: **one skill with modes.** The artifact-type / activity is a mode parameter; the constraints-profile registry (`constraints.json`, iteration-plan §10) drives per-mode behavior. There is no `spec-crafting` / `design-crafting` split.
- Why: (1) the convergence infrastructure (normalizer, constraints-checker, authority-chain-checker, ODP-tracker, reviewer, verdict-emitter) is **shared** across all modes — a family would duplicate it N times. (Copy-not-import, workspace rule 7, is for small self-contained gates, not for an entire convergence pipeline.) (2) The artifacts form an **authority chain** (spec > blueprint > summary > companion) whose consistency must be checked **across** artifacts — one skill owns the whole chain; a family fragments authority-consistency into a cross-skill coordination problem with no owner. (3) The handoff to `parallel-development` is **one plan-model** (executable subset) — one skill produces it. (4) Precedent: `parallel-development` is itself one multi-mode skill (feature-dev / bug-fix / refactor / e2e / docs × many languages), not a family.
- Rejected: a skill family (duplicates the convergence pipeline N×; fragments authority-chain consistency; fragments the plan-model handoff); one-skill-per-artifact (same problems, worse — 4–5 skills each carrying a copy of the pipeline).

## 7. Research constraints-profile: adopt the universal subset, defer the KB-platform parts

- Context: arch-design §3 lists the research constraints-profile after `ws-wiki/fedaot-kb`: sources-cited, staging-status, trust/provenance-tier, direction-normalized (idempotency), cost-bounded, purity-filter. ODP-4 asked: adopt all verbatim, or a subset? fedaot-kb is a knowledge-base platform; blueprint-crafting's research feeds the upstream spec/design/plan pipeline — some constraints are universal to research-as-constrained-production, others are KB-platform-specific.
- Decision: v1 adopts the subset that defends research's universal, pre-use-detectable failure modes; the rest are deferred or dropped.
  - **Keep (v1)**: sources-cited (Blocker — every claim → a fetched source; defends against hallucination); staging-via-convergence (Blocker — research flows through the convergence loop before being frozen into the plan-model; the analog of fedaot-kb's staging queue); cost-bounded (Blocker when exceeded — declared budget, early-terminate); provenance-tag (warning — each source tagged by type: official-spec / peer-reviewed / vendor-doc / blog / unknown).
  - **Defer**: direction-normalized idempotency (a cost optimization, not a correctness constraint — v1.x); full trust-tier classification (v1 ships the light provenance tag; full Tier1/2/3 promotion-gating later).
  - **Drop**: fedaot-kb purity-filter (KB-specific: "reusable knowledge vs implementation detail"). blueprint-crafting's research output is not a KB entry — the artifact completeness-checker (the artifact's own anchors) serves the analogous role.
- Why: keep what catches research's universal failure modes (unsourced hallucination, unbounded cost, unreviewed publication); drop what is KB-platform-specific (purity) or optimization-only (idempotency). Light provenance tagging gives source-quality signal in v1 without the full tiering machinery.
- Rejected: "adopt fedaot-kb verbatim" (brings KB-platform machinery — staging-queue-as- separate-infra, full tiering, purity — that does not map cleanly to a spec-feeding research activity); "sources-cited only" (loses cost-bounded → unbounded cost; loses staging → research frozen unreviewed); "drop provenance entirely" (loses source-quality signal — a claim from an official spec vs a blog matters).

## 8. The activation-boundary test asserts the description surface, not a deterministic router

- Context: iteration-plan I0 requires a bidirectional trigger test — activation-positive phrases route here, activation-negative phrases route to parallel-development, and the scope guard emits out-of-scope for "implement code." But activation routing is ultimately the consuming model's call at runtime (it tokenizes the `description` frontmatter and decides); there is no deterministic router in the loop to assert against. A test that tried to prove "the model WILL route X here" would be testing the model, not the skill — uncodable. A second trap: blueprint-crafting's description legitimately contains generic code words ("implement", "code") in a routing-negation ("NOT for implementing code"); distinguishing a positive trigger from a routing-negation is not deterministically decidable from the description surface.
- Decision: the trigger test asserts the description SURFACE, in four strict checks: (1) positive coverage — each activation-positive phrase has a keyword in this skill's description; (2) no positive steal — the description contains none of parallel-development's distinctive keywords (TDD / red-green / test-first / convergent-fix-loop), chosen so this skill can avoid them entirely, even in negation; (3) parallel-dev reachable — parallel-development's description claims the implementation domain (one global check, not per-phrase); (4) scope guard structural — SKILL.md has a Scope Guard naming code as out-of-scope, routed to parallel-development. The `negative` phrase list is surfaced as a coverage note for human review, not machine-asserted per-keyword (the seam).
- Why: these four are all deterministically decidable from the artifacts on disk, and together they bound the activation collision risk (I0's stated risk) without pretending to test the model. Surfacing the seam honestly (rule 3) prevents a future maintainer from over-trusting the gate as a routing proof.
- Rejected: "assert each negative phrase is in parallel-development's description" (brittle — parallel-development's description does not enumerate every code-request synonym; "fix this bug" routes to parallel-development even though its description lacks the word "bug"); "per-keyword collision check treating every code word as theft" (false-positives on the routing-negation; the negation seam is undecidable); "test the model directly" (testing the wrong thing — the skill, not the model, is the unit).

## 9. Plan-model item fields are classified three-way (executable / upstream_only / downstream_only)

- Context: ADR #1 fixed the executable subset (item_id / seq / depends_on / dod_ref) as the lossless round-trip contract, but the plan-model item carries ~12 fields total. They needed an explicit classification so a consumer knows which fields are the contract, which are tagged extensions, and which have no upstream source. The risk of leaving it implicit: a maintainer adds a field and silently breaks either the round-trip (putting a code-execution concern into the executable subset) or the honesty (sourcing `blueprint_subset` upstream, which has no upstream source).
- Decision: a three-way split, declared once as the `EXECUTABLE_SUBSET` / `UPSTREAM_ONLY` / `DOWNSTREAM_ONLY` constants in `infra/scripts/plan_model.py` and mirrored verbatim in the schema's `subset_tags`. `executable` = the lossless contract (consumed by parallel-development). `upstream_only` = metadata this skill sources (title / scope / source_location / complexity / risk / odp_status / constraints_profile / parallel_group), tagged and ignored downstream. `downstream_only` = `blueprint_subset` alone — a code-execution concern with NO upstream source; `project_plan_model_item` always emits it empty, and a lift preserves a downstream value as data (its origin conveyed by the classification, not a per-item tag). The schema uses `additionalProperties: false` so an undeclared field is a hard error, forcing every new field to declare its subset.
- Why: the three-way split makes ADR #1's field-level consequence (blueprint_subset is downstream-only and empty at round-trip) a structural invariant, not a convention. Mirroring the classification in both the constant and the schema closes the drift gap; `additionalProperties: false` turns "forgot to classify a new field" into a failing test.
- Rejected: "two-way split (executable + the rest)" (collapses upstream-only and downstream-only; loses the distinction that makes blueprint_subset's empty-at-round-trip honest — a maintainer could not tell which "rest" field is unsourced); "a per-item provenance tag on blueprint_subset" (breaks `additionalProperties: false`; redundant with the classification; rejected during I1 implementation when it failed schema validation); "relax additionalProperties to allow ad-hoc fields" (loses the forcing function that keeps the classification complete).

## 10. plan_reviewer precision is an outer-ring eval, not a deterministic gate

- Context: iteration-plan I5's DoD is "the reviewer hits the CORRECT planted defect" (precision; rule 4: no Blocker-on-a-guess). But the plan_reviewer IS the outer ring — an adversarial LLM agent spawned in a fresh context. Its output is a model judgment, not a compile. Making "the LLM hit the correct defect" a deterministic gate would violate rule 4 (heuristics/LLM judgments are advisory, never a deterministic Blocker) and rule 3 (a gate that cannot deterministically enforce something must degrade honestly, not fake green). The naive reading of I5's DoD — "a Python test that passes only when the reviewer is precise" — is not realizable as a compile.
- Decision: split I5 into two layers, mirroring agent-crafter's own validate-vs-evaluate split. (1) A DETERMINISTIC GATE (`plan_reviewer_precision.py`'s `validate_fixture`, runs in the gate suite): validates the scaffolding that makes a precision eval meaningful — each fixture's plan-model is schema-valid (so the planted defect is SEMANTIC, not structural — the inner ring would not catch it; that is the outer ring's job), the planted defect's markers are actually present (ground truth — the fixture is honest), and `expected_findings` conforms to the findings schema and targets the planted defect_id. (2) A PRECISION ASSERTION (`assert_precision(reviewer_output, fixture)`, deterministic GIVEN a reviewer's output): the convergence loop spawns the agent, captures its JSON, then calls this to verify it hit the planted defect_id at the planted severity/kind with evidence citing the location, and respected the outcome axis. The LLM spawn is the non-deterministic part; the check is fully deterministic once output exists.
- Why: this keeps the gate suite deterministic and honest (rule 1: self-checks are DoD; rule 4: no LLM-Blocker) while still delivering a real, runnable precision measurement (the assert is exact — wrong severity, missed defect, or outcome-axis overreach all fail it). The defect kinds are chosen to be SEMANTIC (contradiction, over-engineering, unfalsifiable DoD) so the fixtures exercise the outer ring's actual value-add over the inner ring.
- Rejected: "a Python test that spawns the reviewer and asserts precision at compile time" (non-deterministic — flaky gate; violates rule 4; a Python script cannot spawn a Claude subagent anyway); "precision as a pure documentation claim with no assert" (rule 3 — silent; nothing actually checks precision); "plant only structural defects the inner ring catches" (tests the wrong ring — the outer ring's value is the semantic defects the inner ring misses).

## 11. Field isolation is structurally enforced, not conventional

- Context: arch-design §5 requires the process/outcome axes be kept separate — `rightness` must never change with `process_converged`. A conventional approach ("rightness is always the constant by code discipline") risks a future maintainer wiring `process_converged` into `rightness`, silently breaking the separation the verdict's honesty depends on (a consumer would misread a green process axis as outcome success).
- Decision: enforce field isolation STRUCTURALLY in three layers. (1) `rightness` is a JSON-Schema enum with exactly ONE value (`human_confirm_required`) — the schema cannot validate any other value. (2) `verdict.emit` assigns the constant UNCONDITIONALLY — it never reads `process_converged` when setting `rightness`. (3) `run_record.py` asserts byte-identical `rightness` across a green and a red scenario (the I6 DoD), proving the two diverge only on `process_converged`.
- Why: structural enforcement turns the isolation into a compile/test-time invariant, not a convention. A maintainer cannot break it without changing the schema enum AND the emitter AND the test simultaneously — three independent guards.
- Rejected: "rightness is always the constant by convention" (fragile — a silent one-line break); "two separate schemas for process/outcome" (overkill — one record, two fields, is the point); "rightness omitted when not converged" (wrong — the constant is the point; omission invites a consumer to infer).

## 12. Heuristic anchor detection degrades to coverage, not Blocker; provenance-tagged

- Context: the I3 constraints-checker treats a missing required anchor as a Blocker (a real structural absence — the I3 DoD). The iteration-plan §10 dogfood requires the normalizer to EXTRACT the `anchors` map from real docs via keyword detection — a heuristic. If that detection misses an anchor that is actually present, treating the miss as a Blocker would violate rule 4 (no Blocker-on-a-guess) and falsely fail the dogfood. Yet the I3 negative fixture (an author-declared gap) MUST still Block.
- Decision: the anchors map carries provenance via `anchors_meta.source`: `author-supplied` (the map is authoritative — a missing required anchor is a real Blocker) vs `normalizer-extracted` (heuristic — an undetected anchor degrades to a coverage note, rule 4). The checker branches on this. The I3 exemplars/negatives (author-supplied) keep their Blocker semantics; the normalizer's output degrades honestly. A hand-authored map with no `anchors_meta` defaults to author-supplied (backward-compatible).
- Why: this preserves the I3 DoD (author-declared gaps Block) while letting the dogfood use heuristic extraction without false Blockers. The provenance tag is the honest seam — it tells the checker how much to trust the map. Without it, the checker would have to choose between rule-4 violations (always Block) and a broken DoD (never Block).
- Rejected: "always Block on a missing anchor" (rule 4 violation — false Blockers on heuristic misses, and it would fail the real-doc dogfood); "never Block on a missing anchor" (breaks the I3 DoD — author-declared gaps must Block); "a confidence threshold on anchor entries" (over-engineered for two provenance cases).

## 13. Researcher subagent: sourcing/convergence split (modifies #3/#4)

- Context: ADR #3 makes research a constrained-production activity the skill authors/rewrites/researches in the main context; ADR #4 fixes research's convergence oracle as its constraints-profile (`research_constraints.py`). The trap: multi-source web gathering produces verbose fetch output that bloats the main context — the exact cost the subagent mechanism exists to isolate. But moving research OUT of the main context risks splitting the convergence oracle from the activity, or silently introducing a `research-notes` normalizer parser that does not exist (`normalizer.py` has 3 parsers — `cursor-plan`/`work-package`/`rich-md` — all emitting an `items[]` shape; none emit the `research.{claims,sources,cost_ledger,staging}` sub-object `research_constraints.py` reads).
- Decision: add a `solidforge:researcher` subagent that performs ONLY web/codebase sourcing and returns the `research` sub-object directly (the exact shape `research_constraints.py` consumes: `claims[]{text, source_refs[]}`, `sources[]{source_id, fetched, provenance}`, `cost_ledger{budget, used}`, `staging{in_staging, converged}`). The convergence loop (main context) places it into `plan_model["research"]`, **bypassing the item-normalizer** — consistent with how research artifacts already acquire that field (no item-parser produces it). The convergence oracle stays in `research_constraints.py`; conclusion truth stays outcome-axis (human). Dispatch ONLY for multi-source web gathering; trivial/codebase-only research stays self-authored per ADR #3.
- Why: gains context isolation for the expensive part (web I/O) without touching the deterministic convergence oracle or the normalizer. The researcher is a producer feeding an existing consumer shape — no new schema, no new parser, no new gate. Bounding the dispatch (multi-source only) keeps ADR #3's self-authoring as the default and the researcher an opt-in tool.
- Rejected: (a) main-context self-authoring only (= ADR #3 status quo — keeps verbose web I/O in the main context); (b) a researcher that judges conclusion truth (violates the outcome axis); (c) researcher with Edit/Write to stage its own output (staging→freeze is human-gated per ADR #4's `staging-via-convergence`); (d) implement a `parse_research_notes` normalizer parser (scope-creep — research artifacts bypass item-normalization, so a parser has no consumer); (e) route blueprint research to the `deep-research` skill (it emits a cited report, not the `research` sub-object, and does not pass `research_constraints.py`).
- Coverage note: the researcher assumes blueprint-crafting wins activation. The blueprint-vs-`deep-research` **skill-level** activation collision is orthogonal and unaddressed here.

## 14. plan-reviewer `tools:` frontmatter enforces the read-only contract at the tool layer

- Context: `plan-reviewer`'s body states "report only, never fix — read-only tools (Read, Grep, Glob), no Edit/Write." But the agent had NO `tools:` frontmatter, so it inherited all tools including Edit/Write — the diagnose/repair split was enforced by prose only. A reviewer that can Edit can silently mutate the artifact it is supposed to only judge.
- Decision: add `tools: Read, Grep, Glob` + `disallowedTools: Edit, Write, NotebookEdit` to the agent frontmatter. Plugin subagents honor `tools`/`disallowedTools` (only `permissionMode`/`hooks`/`mcpServers` are ignored for plugin agents), so `tools:` is the enforceable mechanism; `permissionMode` would be a no-op. Runtime verification (resolved tool list excludes Edit/Write) is ground truth; if a future loader change stops honoring `tools:`, fall back to `disallowedTools`-only.
- Why: the contract becomes mechanically enforced at the tool layer, not a convention a future maintainer could break by editing prose. Belt-and-suspenders (`tools` + `disallowedTools`) covers either honor mode.
- Rejected: `permissionMode` (ignored for plugin agents — silent no-op, rule 3 violation); "prose-only enforcement" (the original gap — a reviewer with Edit access defeats the diagnose/repair split). NOTE: this is a PLUGIN-LEVEL concern (frontmatter semantics for any plugin agent), filed here in blueprint-crafting's log because `plan-reviewer` is blueprint's agent; no plugin-level ADR log exists today.

## 15. Anchor detection is bilingual (English + Chinese), still heuristic; over-detection is safe

- Context: ADR #12 lets an undetected anchor degrade to a coverage note when `anchors_meta.source = normalizer-extracted` (rule 4: no Blocker-on-a-heuristic-miss). The detector (`normalizer.extract_anchors`) matches keywords from the registry (`constraints.json → anchor_detection`). That map was English-only, so on a Chinese-language artifact EVERY anchor missed → the inner ring's completeness check was vacuous (nothing verified, all coverage). A user hit this and had to hand-author an `author-supplied` map. The English-only detector made the rule-4 degradation correct but useless for the workspace's primary non-English language.
- Decision: make `anchor_detection` **bilingual** — every one of the 27 profile anchors carries English + Chinese aliases (registry-only, rule 2; no checker or `extract_anchors` logic change — it already does Unicode substring + `#`-heading matching). Detection stays a heuristic: the normalizer still tags `normalizer-extracted`, so a miss still degrades to coverage per ADR #12 (rule 4 unchanged). Over-detection is SAFE — a spurious `present=True` cannot manufacture a Blocker, because the source stays `normalizer-extracted`; only an `author-supplied` map is authoritative (a gap is a Blocker there). For docs the aliases still under-detect (a third language, unusual terminology), the author-supplied escape hatch (ADR #12) remains the strong path.
- Why: this restores the inner ring's actual value (completeness verification) on Chinese artifacts without weakening any rule-4 / ADR-#12 guarantee. The asymmetry — under-detection is harmful (hides the check), over-detection is harmless (no false Blocker) — makes broad Chinese aliases strictly safe to add. Keeping it registry-driven (not an `extract_anchors` code branch) preserves rule 2 and the determinism-over-the-model contract (ADR #2).
- Rejected: (a) an LLM-based or runtime-translation anchor detector — non-deterministic, violates rule 4 (a heuristic pretending to be a deterministic gate) and ADR #2's model-level determinism, and too costly for the convergence hot loop (the loop-integration-cost constraint); (b) Block-on-a-Chinese-miss — violates rule 4 / ADR #12 and would falsely fail real Chinese docs; (c) English-only detection + doc-only "author-supply the map" workaround — leaves the inner ring vacuous for Chinese (the reported gap; the workaround is an escape hatch, not the default path); (d) a per-anchor confidence threshold — over-engineered for what is, after ADR #12, a coverage-not-Blocker heuristic.

## 16. `produce.py` is the runtime production orchestrator; operators chain as library calls, not shell CLIs

- Context: the operators (`normalizer`, `constraints_check`, `verdict`, `freeze`) each ship a `__main__` CLI, but the CLIs are NOT shell-pipeable — `normalizer` prints a `{plan_model, coverage}` wrapper while `constraints_check` / `verdict` / `freeze` each `json.load` the input and treat it as a bare plan-model. Chaining them on the shell feeds the wrong shape and fails silently green (the checker sees `artifact_type=None`, finds no profile, returns `passed=True` — a rule-3 violation). With no runtime entry point, an LLM invoking the skill explored `infra/scripts/*.py` to reverse-engineer a CLI that did not exist; `end_to_end.py` chains the operators as library calls, but it is a test, not a production entry.
- Decision: add `produce.py` as the one-command production entry point. It chains `constraints_check` / `research_constraints` → `verdict.emit` → `freeze.freeze` as LIBRARY calls (no subprocess, no shell pipe), so the format mismatch is bridged in-process and can never silently pass. The outer ring (`solidforge:plan-reviewer`) is an LLM agent and is NOT run inside the CLI; its findings are injected via `--outer` (absent → `verdict` `outer={}`, the run-record coverage-notes the outer ring did not run, `process_converged` stays false). Authoring the Markdown artifact + the plan-model's anchors/items stays the LLM's job — `produce.py` takes an already-authored bare `plan-model.json`. `freeze.freeze` gained an optional `outer=None` kwarg so `produce` composes it rather than duplicating the freeze logic (rule 7).
- Why: the deterministic chain (inner → verdict → freeze) is identical every run and has no judgment to defer beyond the one-time invocation — exactly the shape that wants a single entry point. Keeping the outer ring OUT of the CLI (injected via `--outer`) preserves the deterministic/adversarial split (ADR #10: plan-reviewer is an eval, not a gate) and the honest-degradation contract (an unrun outer ring is coverage-noted, never a silent green). Library calls (not shell pipes) are the only form that can bridge the operator format mismatch without a silent-green trap.
- Rejected: (a) shell-chaining the operator CLIs (`normalizer | constraints_check | verdict | freeze`) — format mismatch + silent green (the Context); (b) `produce.py` runs the outer ring itself — the plan-reviewer is an LLM agent (ADR #10), not a deterministic step a CLI can invoke; running it inside would either fake or block on an LLM call; (c) `produce.py` also authors the artifact/anchors — that is the LLM's producer role (ADR #3); the orchestrator converges an authored model, it does not author; (d) a single end-to-end "produce everything including outer" command — hides the deterministic/adversarial boundary behind one exit code, undoing the field isolation (ADR #11) at the entry-point layer.

## 12. facade-impact-assessment — a required iteration-plan anchor (advisory content; surfaces the facade-doc question at planning time)

- Context: an observed recurring gap — pd completions never auto-synced project facade docs (README/USER_GUIDE/GitHub About) when a new user-visible capability landed; a human always had to prompt "now update the docs." Root cause spans two layers: CLAUDE.md rule 5's doc-audit enumeration named only skill-internal references (no facade docs), and bc's iteration-plan anchors had no "does this capability change user-visible behavior, and which facade sections go stale?" anchor. bc is the only phase that sees the whole capability (pd sees items; csr/psv see one artifact), so the leverage point is bc planning time. This ADR is tier 1 of 3 (tier 2 = a pd outer-ring facade-drift advisory check; tier 3 = a dedicated facade-reviewer leg — both deferred).
- Decision: add `facade-impact-assessment` as a required iteration-plan anchor (registry: constraints.json; human list: arch-design §3; author doc: iteration-plan.md §Facade). Semantics mirror every existing anchor — **presence required** (bc Blocks an author-supplied plan that omits it; coverage note when normalizer-extracted), **content advisory** (a plan that honestly states "no facade impact" passes; correctness of that call is human/outer-ring, never a Blocker — rule 4, because facade drift is a semantic judgment, not grep-able). Plus CLAUDE.md rule 5 gains facade docs as an advisory doc-audit target.
- Why: the gap was implicit — turning it into an EXPLICIT question bc must answer (and pd can read in the frozen plan) is the forcing function. Advisory (not Blocker) on content because "is this README sentence now stale?" is uncodable (rule 4); presence is required because that is codable and is the actual failure mode (the question was never asked).
- Rejected: (a) tier 2 only (a pd-time facade-drift gate) without the bc anchor — pd sees items, not the whole capability, so it cannot reliably ask the facade question; bc planning time is the leverage point. (b) Blocker severity on facade drift — would Block on an uncodable semantic guess, violating rule 4; facade content stays advisory. (c) a separate "facade-sync" pipeline stage — over-engineering for tier 1; the anchor + rule-5 bullet are the minimal forcing function. (d) dogfooding via a separate full csr→bc→pd run on a sidecar proposal — disproportionate for a ~7-file registry/doc edit; the plan was instead run through solidforge's two read-only quality legs (csr same-family doc-reviewer + bc outer-ring plan-reviewer), which found 6 real defects folded before implementation (the dogfood self-bootstrap). (e) the "fires on its own introduction" framing — logically impossible (the anchor's registry entry cannot exist before the change that adds it); dropped.
